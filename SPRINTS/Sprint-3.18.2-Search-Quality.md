---

## Known technical findings

### Finding 1 - relevance threshold

`CareerSearchWorkflow` currently uses:

`minimum_skill_matches = 2`

A job is relevant when:

- `job.score > 0`

AND either:

- the job title matches the selected role;
- enough exact `matched_skills` exist.

### Finding 2 - duplicated skill knowledge

The CV extraction pipeline uses:

`src.ai.skill_dictionary.SKILL_SYNONYMS`

This shared dictionary now contains Finance skills.

The matching pipeline also contains:

`src.matching.skill_dictionary.SKILL_ALIASES`

This second dictionary is much smaller and historically IT-oriented.

This can cause the CV to understand a Finance synonym while job matching does not.

### Finding 3 - semantic evidence

`SkillMatcher` can produce:

- exact matches;
- semantic/category matches;
- graph matches.

`CareerSearchWorkflow.filter_jobs()` currently uses only `job.matched_skills`.

Semantic matches can contribute to the score but are not counted as relevance evidence.

### Finding 4 - Career role context

Inspect whether the selected Career role reaches the Workspace search flow correctly.

Do not assume it does.

## Implementation requirements

### A. Shared alias knowledge

Remove the effective divergence between the Finance-capable shared skill dictionary and job matching.

Preferred direction:

`SkillMatcher` should be able to use `SKILL_SYNONYMS` as shared alias knowledge.

Do not blindly delete `src/matching/skill_dictionary.py` if existing compatibility depends on it.

A safe adapter/merge strategy is acceptable.

Existing IT aliases must remain functional.

---

### B. Finance matching tests

Add tests proving examples such as:

Profile skill:

`pilotage budgétaire`

Job text:

`pilotage du budget`

Expected:

recognized match.

Profile skill:

`contrôle de gestion`

Job text:

`dialogue de gestion`

Expected:

recognized match.

Profile skill:

`trésorerie`

Job text:

`suivi de tresorerie`

Expected:

recognized match.

Preserve false-positive protection.

---

### C. Relevance evidence

Review `CareerSearchWorkflow.filter_jobs()`.

Do not consider only exact matches if the matching engine has produced valid semantic evidence.

Define an explicit relevance-evidence calculation.

Possible evidence:

- exact matches;
- semantic matches;
- title match.

The implementation must remain explainable and tested.

Do not silently convert semantic matches into exact matches.

---

### D. Search diagnostics

Introduce a small structured diagnostic model or equivalent result data for filtering.

For each processed job, it should be possible to know at least:

- score;
- exact match count;
- semantic match count;
- title match;
- accepted/rejected;
- rejection reason.

Avoid `print()` debugging in production code.

Aggregate diagnostics should make a case such as:

`126 collected / 0 relevant`

explainable.

Examples of rejection reasons:

- `zero_score`
- `insufficient_relevance_evidence`

Do not introduce excessive complexity.

---

### E. CareerSearchResult

If appropriate, expose aggregate filter diagnostics through `CareerSearchResult`.

Keep backwards compatibility for existing callers.
